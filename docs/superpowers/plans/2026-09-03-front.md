# Front — plan d'implémentation

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Construire l'application React qui remplace le dashboard Streamlit,
en consommant l'API FastAPI déjà implémentée (plans « socle et ingestion »,
« ingestion étendue », « analytics et API », « photos et écritures »,
tous terminés). Neuf routes, dans l'ordre de la spec section 10 point 6 :
`/`, `/corps`, `/entrainement` + `/entrainement/:id`, `/phases` +
`/phases/:id`, `/energie`, `/nutrition`, `/corps/photos`, `/reglages`.

**Architecture:** Vite + React + TypeScript. Trois étages sans dépendance
circulaire : `api/` (fetch typé, un module par domaine backend, aucune
connaissance de React) ; des hooks TanStack Query minces au-dessus de
`api/`, un par requête, qui portent le cache et l'invalidation ; des pages
sous `routes/` qui n'appellent jamais `fetch` directement, seulement les
hooks. Les composants de présentation (cartes, anneaux, graphiques) sont
purs — ils reçoivent des données déjà typées, jamais une réponse HTTP brute.
Aucun calcul métier côté front : tout est déjà agrégé par le back
(spec section 3.1) — le front trace ce qu'on lui donne.

**Tech Stack:** Vite, React 18, TypeScript, React Router, TanStack Query v5,
Tailwind v4, shadcn/ui, Recharts (graphiques), MapLibre GL (traces GPS),
Vitest (tests unitaires sur fonctions pures uniquement — pas de test de
rendu, spec section 9). Build statique servi par nginx en production,
aucun runtime Node.

**Spec:** `docs/superpowers/specs/2026-09-02-migration-fastapi-react-design.md`
(section 8 principalement ; section 6 pour le contrat API).

## Global Constraints

- Node `>=20`. Planchers de dépendances, jamais de versions figées :
  `vite>=5.4`, `react>=18.3`, `react-dom>=18.3`, `typescript>=5.6`,
  `react-router-dom>=6.27`, `@tanstack/react-query>=5.59`,
  `tailwindcss>=4.0`, `recharts>=3.10` (2.x est deprecated depuis la sortie
  de la branche 3), `maplibre-gl>=4.7`, `vitest>=2.1`.
- **Aucune URL d'API en dur dans le code applicatif.** Un seul point de
  configuration : `import.meta.env.VITE_API_BASE_URL`, avec `/api` comme
  valeur par défaut en dev (proxifié par Vite vers `http://localhost:8000`).
- **Une valeur absente est `null`, jamais `0`, `"—"` calculé côté client, ni
  masquée.** Le back renvoie déjà `null` pour toute grandeur manquante
  (spec section 4.13) ; le front affiche un état vide explicite (`"—"` en
  rendu, jamais une valeur de remplacement injectée dans un calcul ou un
  graphique). Un point `null` dans une série Recharts casse la ligne au lieu
  de la faire plonger à zéro (`connectNulls={false}`, jamais `true` par
  défaut).
- **Toutes les valeurs numériques s'affichent en monospace** (chiffres
  tabulaires), tous les titres de section en display condensé capitales,
  tout le texte courant en sans-serif — direction visuelle de la spec
  section 8, arrêtée en détail (palette exacte, échelle typographique,
  composants) via la skill `frontend-design` à la tâche 1, et la palette de
  graphiques via la skill `dataviz` à la tâche 4. Aucune tâche suivante ne
  choisit de couleur elle-même : elle réutilise les tokens posés aux tâches
  1 et 4.
- **Fond sombre uniquement, pas de thème clair** — l'application est sombre
  par construction (spec section 8).
- **Aucune page n'appelle `fetch` directement.** Toute requête HTTP passe par
  un module de `src/api/`, appelé par un hook `src/api/*/hooks.ts`, appelé
  par une page. C'est ce qui rend les fonctions de mapping testables sans
  serveur et garantit un seul endroit qui connaît le format RFC 9457.
- **Décimation et agrégation restent côté back.** Le front ne réduit, ne
  moyenne ni ne recalcule jamais une série reçue ; il passe au maximum un
  paramètre de requête (`points`, `resolution`) à l'API.
- Code, noms de fichiers, commits en anglais ; commentaires et documentation
  en français, comme le reste du dépôt.
- Tests : Vitest sur les fonctions pures de `src/lib/format.ts` et
  `src/api/*/mapping.ts` uniquement (parsing de dates, formatage de durée et
  d'allure, construction de query strings, traduction RFC 9457 → message).
  Pas de test de rendu de composant — mauvais rapport valeur/coût sur une
  application personnelle (spec section 9).

## Contrat API de référence

Extrait du code réel du backend (`backend/app/api/*.py`,
`backend/app/schemas/*.py`), c'est la source de vérité pour tous les types
TypeScript du front. Ne pas re-dériver ces types depuis la spec : la spec
décrit l'intention, ce bloc décrit ce que l'API renvoie effectivement.

Format d'erreur global (`app/errors.py`), RFC 9457 :

```ts
interface ProblemDetails {
  type: "about:blank";
  title: string;
  status: number;
  detail: string;
  instance: string;
  errors?: unknown[];     // 422 de validation FastAPI uniquement
  allowed?: string[];     // certaines 422/415 métier (tailles, tags)
}
```

Enums partagées :

```ts
type PhaseKind = "free" | "bulk" | "cut" | "maintain";
type IngestionStatus = "running" | "success" | "failed";
type Metric = "weight" | "body_fat" | "muscle";
type Direction = "up" | "down";
```

Wrappers de pagination :

```ts
interface Page<T> { items: T[]; page: number; page_size: number; total: number; }
interface CursorPage<T> { items: T[]; next_cursor: string | null; }
```

Toutes les routes GET listées ci-dessous acceptent `from?: string /* date */`
et `to?: string /* date */` en query params (alias HTTP `from`/`to`,
inclusifs) sauf mention contraire.

**Corps** (`/api/body`) :
- `GET /measurements` → `MeasurementOut[]`
  `{ at: string; weight_kg: number|null; body_fat_pct: number|null; body_fat_mass_kg: number|null; skeletal_muscle_mass_kg: number|null; fat_free_mass_kg: number|null; total_body_water_kg: number|null; basal_metabolic_rate_kcal: number|null }`

- `GET /calendar?metric&year` (requis) → `{ day: string; value: number|null }[]`
- `GET /composition` → `{ day: string; body_fat_mass_kg: number|null; fat_free_mass_kg: number|null; skeletal_muscle_mass_kg: number|null; total_body_water_kg: number|null; basal_metabolic_rate_kcal: number|null }[]`

**Analytics** (`/api/analytics`) :

**Nutrition** (`/api/nutrition`) :
- `GET /daily` → `{ day: string; calories: number|null; entry_count: number }[]`
- `GET /entries?page=1` → `Page<{ at: string; food_name: string; meal_type_label: string; amount: number|null; unit_label: string; calories: number|null }>`

**Phases** (`/api/phases`) :
- `GET /` → `PhaseOut[]` où `PhaseOut = { id: number; name: string; kind: PhaseKind; starts_on: string; ends_on: string; weight_target_kg: number|null; body_fat_target_pct: number|null; skeletal_muscle_target_kg: number|null; daily_calories_target: number|null; notes: string|null }`
- `POST /` (body `PhaseCreate`, sans `id`) → `201 PhaseOut` ; 422 si `ends_on < starts_on` ; 409 si conflit d'intégrité

- `PATCH /{id}` (body `PhaseUpdate`, tous champs optionnels) → `PhaseOut` ; 404, 422, 409
- `DELETE /{id}` → `204`

- `GET /workouts?sport&limit&cursor` → `CursorPage<WorkoutSummaryOut>` où `WorkoutSummaryOut = { id: number; sport: string; started_at: string; ended_at: string|null; duration_ms: number|null; distance_m: number|null; calories_kcal: number|null; mean_heart_rate: number|null }`

- `GET /workouts/{id}` → `WorkoutDetailOut` (tous les champs de `WorkoutSummaryOut` plus `sport_type, max_heart_rate, min_heart_rate, mean_speed_mps, max_speed_mps, mean_cadence, max_cadence, min_altitude_m, max_altitude_m, altitude_gain_m, altitude_loss_m, pool_length_m, resting_hr, has_samples, has_locations, has_swim_lengths, has_strength_sets` — tous `number|null` sauf les `has_*` en `boolean`) ; 404
- `GET /workouts/{id}/samples?points=1000` → `{ at: string; heart_rate: number|null; speed_mps: number|null; distance_m: number|null; cadence: number|null; altitude_m: number|null }[]` ; 404
- `GET /workouts/{id}/track` → `{ type: "LineString"; coordinates: [number, number][] }`
- `GET /workouts/{id}/splits?unit=km` → `{ index: number; distance_m: number; duration_s: number; pace_s_per_km: number|null; mean_heart_rate: number|null }[]`
- `GET /workouts/{id}/hr-zones` → `{ zone: number; label: string; seconds: number }[]` ; 422 si `max_hr` indisponible
- `GET /workouts/{id}/swim` → `{ stroke_type: string; length_count: number; mean_swolf: number|null; mean_duration_s: number|null }[]`
- `GET /workouts/{id}/strength` → `{ sets: { idx: number; reps: number|null; weight_kg: number|null; duration_s: number|null }[]; set_count: number; total_volume_kg: number|null; total_reps: number|null }`

**Photos** (`/api/photos`, monté séparément, pas de double préfixe) :
- `GET /?tag` → `PhotoOut[]` où `PhotoOut = { id: number; taken_on: string; tag: string; width: number|null; height: number|null; byte_size: number|null; content_type: string|null; created_at: string }`
- `POST /` multipart (`taken_on`, `tag` parmi `face|profil|dos|bras|epaule`, `file`) → `201 PhotoOut` ; 415 (tag/format), 413 (taille), 409 (doublon sha256)
- `DELETE /{id}` → `204` ; 404
- `GET /{id}/image?size=thumb|medium|full&blur=false` → binaire (`image/jpeg`), pas de schéma JSON ; 422 si `size` invalide, 404

**Imports** (`/api/imports`) :
- `POST /samsung-zip` multipart (`file`) → `202 IngestionRunOut` où `IngestionRunOut = { id: number; kind: string; source_name: string; status: IngestionStatus; started_at: string; finished_at: string|null; counts: Record<string, unknown>|null; error: string|null }` ; 422 si signature ZIP invalide
- `GET /` → `IngestionRunOut[]`
- `GET /{id}` → `IngestionRunOut` ; 404 — le front poll cet endpoint jusqu'à `status !== "running"`

- [ ] **Step 4 : implémenter `query-string.ts`**

```ts
export function buildQueryString(params: Record<string, unknown>): string {
  const search = new URLSearchParams();
  for (const [key, value] of Object.entries(params)) {
    if (value === undefined || value === null) continue;
    const serialized = value instanceof Date ? formatDateParam(value) : String(value);
    search.set(key, serialized);
  }
  const query = search.toString();
  return query ? `?${query}` : "";
}

function formatDateParam(date: Date): string {
  const year = date.getFullYear();
  const month = String(date.getMonth() + 1).padStart(2, "0");
  const day = String(date.getDate()).padStart(2, "0");
  return `${year}-${month}-${day}`;
}
```

```ts
import type { ProblemDetails } from "./types";

const BASE_URL = import.meta.env.VITE_API_BASE_URL ?? "/api";

export class ApiError extends Error {
  readonly status: number;
  readonly problem: ProblemDetails;

  constructor(status: number, problem: ProblemDetails) {
    super(problem.detail);
    this.status = status;
    this.problem = problem;
  }
}

export async function request<T>(path: string, init?: RequestInit): Promise<T> {
  const response = await fetch(`${BASE_URL}${path}`, {
    headers: { Accept: "application/json", ...init?.headers },
    ...init,
  });
  if (!response.ok) {
    const problem = (await response.json()) as ProblemDetails;
    throw new ApiError(response.status, problem);
  }
  if (response.status === 204) return undefined as T;
  return (await response.json()) as T;
}
```

```ts
export function formatDuration(ms: number): string {
  const totalSeconds = Math.round(ms / 1000);
  const hours = Math.floor(totalSeconds / 3600);
  const minutes = Math.floor((totalSeconds % 3600) / 60);
  const seconds = totalSeconds % 60;
  const paddedSeconds = String(seconds).padStart(2, "0");
  if (hours > 0) {
    return `${hours}:${String(minutes).padStart(2, "0")}:${paddedSeconds}`;
  }
  return `${minutes}:${paddedSeconds}`;
}

export function formatPace(secondsPerKm: number | null): string {
  if (secondsPerKm === null) return "—";
  const minutes = Math.floor(secondsPerKm / 60);
  const seconds = Math.round(secondsPerKm % 60);
  return `${minutes}:${String(seconds).padStart(2, "0")}/km`;
}

export function formatDelta(value: number | null, unit: string): string {
  if (value === null) return "—";
  const sign = value > 0 ? "+" : value < 0 ? "−" : "";
  const magnitude = Math.abs(value).toFixed(1);
  return `${sign}${magnitude} ${unit}`;
}
```

### Tâche 14 : conteneurisation et intégration finale

**Files:**
- Create : `frontend/Dockerfile`, `frontend/nginx.conf`
- Modify : `compose.yaml` (ajoute le service `web`)

**Interfaces:**
- Consumes : le build de production de toutes les tâches précédentes.
- Produces : service Docker `web` servant le front en statique et
  proxifiant `/api` vers `api:8000`.

- [ ] **Step 1 : Dockerfile multi-stage**

`frontend/Dockerfile` :

```dockerfile
FROM node:22-alpine AS build
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM nginx:1.27-alpine
COPY --from=build /app/dist /usr/share/nginx/html
COPY nginx.conf /etc/nginx/conf.d/default.conf
```

- [ ] **Step 2 : configuration nginx**

`frontend/nginx.conf` :

```nginx
server {
    listen 80;
    root /usr/share/nginx/html;

    location /api/ {
        proxy_pass http://api:8000/api/;
        proxy_set_header Host $host;
    }

    location / {
        try_files $uri $uri/ /index.html;
    }
}
```

- [ ] **Step 3 : ajouter le service au compose**

Dans `compose.yaml`, sous `services:`, ajouter :

```yaml
  web:
    build:
      context: ./frontend
      dockerfile: Dockerfile
    ports:
      - "8080:80"
    depends_on:
      - api
```

- [ ] **Step 4 : vérification**

```bash
docker compose up -d --build web
curl -sf http://localhost:8080/ > /dev/null && echo "front OK"
curl -sf http://localhost:8080/api/health
```

Expected: `front OK` puis `{"status":"ok"}`.

- [ ] **Step 5 : commit**

```bash

git commit -m "feat(front): containerize the front and wire it into compose"
```
